Importar SMB para o Files padrão do Nextcloud

Origem Windows/Samba em 192.168.15.1, staging no disco dedicado, verificação por checksum e publicação atômica para um usuário.

Etapas: Modelo Variáveis Descobrir share Montar Copiar Publicar Validar Limpar

0Modelo recomendado

A VM Nextcloud lê o compartilhamento antigo como somente leitura. A primeira cópia vai para um staging fora do data directory. Somente após a validação o diretório completo é movido, no mesmo filesystem, para o Files do usuário. 
//192.168.15.1/SHARE  (SMB read-only)
          │
          ▼ rsync
/srv/nextcloud-storage/import-staging/IMPORT_ID
          │
          ▼ mv no mesmo ext4
/srv/nextcloud-storage/app-data/USUARIO/files/PASTA
          │
          ▼ occ files:scan
Nextcloud → Arquivos/Files → PASTA
Este procedimento importa para a área privada de um usuário. Para uma pasta compartilhada por grupos, configure primeiro o app Team folders/Group folders; não copie diretamente para a estrutura interna desse app.

1Definir origem e destino

Execute como root na VM Nextcloud. Ajuste os quatro valores iniciais e mantenha a mesma sessão shell aberta até o fim:

set -euo pipefail

SMB_HOST="192.168.15.1"
SMB_SHARE="NOME_DO_SHARE"
SMB_SUBDIR=""  # vazio importa o share inteiro
NC_USER="felipe"
IMPORT_NAME="Importado-servidor-antigo-$(date +%Y-%m-%d)"

SMB_MOUNT="/mnt/importacao-smb"
SOURCE="$SMB_MOUNT${SMB_SUBDIR:+/$SMB_SUBDIR}"
STAGING_ROOT="/srv/nextcloud-storage/import-staging"
STAGING="$STAGING_ROOT/$IMPORT_NAME"
DATA_ROOT="/srv/nextcloud-storage/app-data"
DESTINATION="$DATA_ROOT/$NC_USER/files/$IMPORT_NAME"
CREDENTIALS="/root/.legacy-smb-credentials"
Resultado esperado: nenhuma saída. Use um usuário Nextcloud existente e o nome exato do compartilhamento SMB.

Antes de cada bloco executado em uma nova sessão shell, redefina as variáveis acima e valide:

: "${SMB_HOST:?SMB_HOST não definido}"
: "${SMB_SHARE:?SMB_SHARE não definido}"
: "${NC_USER:?NC_USER não definido}"
: "${SMB_MOUNT:?SMB_MOUNT não definido}"
: "${SOURCE:?SOURCE não definido}"
: "${CREDENTIALS:?CREDENTIALS não definido}"

[[ "$SMB_SHARE" != "NOME_DO_SHARE" ]] || {
  echo "Substitua NOME_DO_SHARE pelo nome real" >&2
  exit 1
}

Valide o destino antes de copiar:

docker exec -u www-data nextcloud-app \
  php occ user:info "$NC_USER"

      docker exec -u www-data nextcloud-app \
        php occ app:list | sed -n '/Enabled:/,/Disabled:/p'

      findmnt /srv/nextcloud-storage
test -d "$DATA_ROOT/$NC_USER/files"
test ! -e "$DESTINATION"
test ! -e "$STAGING"
df -hT /srv/nextcloud-storage
Resultado esperado: o usuário é exibido; o mount é /dev/sdb1 em ext4; os dois testes de inexistência não produzem saída; existe espaço suficiente. O app encryption não deve estar habilitado.
Se a criptografia server-side do Nextcloud estiver habilitada, não faça importação direta no filesystem. Nesse caso, envie os arquivos pelo cliente Nextcloud ou WebDAV para que sejam criptografados pelo aplicativo.

2Testar rede e descobrir o share

apt-get update
apt-get install -y cifs-utils smbclient rsync

ip route get "$SMB_HOST"
timeout 5 bash -c "</dev/tcp/$SMB_HOST/445"
echo "Porta SMB acessível"

smbclient -L "//$SMB_HOST" -U admin -m SMB3

O smbclient solicitará a senha sem gravá-la no histórico. Copie o nome exibido na coluna Sharename para SMB_SHARE.

Resultado esperado: a rota usa a interface da rede local, aparece “Porta SMB acessível” e a listagem mostra um ou mais itens do tipo Disk.
Não prossiga se a porta 445 falhar, se a rota estiver incorreta ou se o share não aparecer. Não reduza para SMB1; tente SMB 3.0 e, somente para equipamento legado conhecido, SMB 2.1.

3Criar credencial temporária e montar

set -euo pipefail
: "${SMB_HOST:?SMB_HOST não definido}"
: "${SMB_SHARE:?SMB_SHARE não definido}"
: "${SMB_MOUNT:?SMB_MOUNT não definido}"
: "${SOURCE:?SOURCE não definido}"
: "${CREDENTIALS:?CREDENTIALS não definido}"

cd /root
install -d -o root -g root -m 0700 "$SMB_MOUNT"
install -d -o root -g root -m 0700 "$STAGING_ROOT"

read -r -s -p "Senha SMB do usuário admin: " SMB_PASSWORD
echo
umask 077
printf 'username=admin\npassword=%s\n' "$SMB_PASSWORD" \
  >"$CREDENTIALS"
unset SMB_PASSWORD
chmod 0600 "$CREDENTIALS"

mountpoint -q "$SMB_MOUNT" && {
  echo "O mountpoint já está montado" >&2
  exit 1
}

mount -t cifs "//$SMB_HOST/$SMB_SHARE" "$SMB_MOUNT" \
  -o "credentials=$CREDENTIALS,ro,vers=3.0,iocharset=utf8,noserverino,uid=0,gid=0,file_mode=0444,dir_mode=0555"

[[ "$(findmnt -n -o FSTYPE --target "$SMB_MOUNT")" == "cifs" ]]
findmnt -n -o OPTIONS --target "$SMB_MOUNT" |
  tr ',' '\n' | grep -Fx ro
findmnt --target "$SMB_MOUNT"
test -d "$SOURCE"
if touch "$SMB_MOUNT/.write-test"; then
  rm -f "$SMB_MOUNT/.write-test"
  echo "ERRO: origem permite escrita" >&2
  exit 1
else
  echo "Origem confirmada como somente leitura"
fi
Resultado esperado: findmnt mostra cifs e a opção ro. O teste mostra a falha “Read-only file system” seguida de “Origem confirmada como somente leitura”.

Se o servidor não aceitar SMB 3.0, desmonte e tente 2.1:

umount "$SMB_MOUNT"

mount -t cifs "//$SMB_HOST/$SMB_SHARE" "$SMB_MOUNT" \
  -o "credentials=$CREDENTIALS,ro,vers=2.1,iocharset=utf8,noserverino,uid=0,gid=0,file_mode=0444,dir_mode=0555"

4Inventariar e copiar para staging

SOURCE_FILES="$(
        find "$SOURCE" -type f -printf '.' | wc -c
)"
SOURCE_BYTES="$(
        find "$SOURCE" -type f -printf '%s\n' |
    awk '{total += $1} END {print total + 0}'
)"

printf 'Arquivos: %s\nBytes: %s\n' \
  "$SOURCE_FILES" "$SOURCE_BYTES"

rsync -rltvn \
  --no-perms --no-owner --no-group \
  --itemize-changes \
  "$SOURCE/" "$STAGING/"
Resultado esperado: o inventário mostra valores plausíveis e o dry-run lista somente arquivos que serão criados. Nenhum arquivo é gravado nesse primeiro rsync.

Faça a cópia real:

rsync -rltv \
  --no-perms --no-owner --no-group \
  --human-readable --info=progress2 \
  --partial \
  "$SOURCE/" "$STAGING/"
Resultado esperado: o progresso chega a 100% e o comando termina com código zero. Uma interrupção pode ser retomada executando exatamente o mesmo comando.

4.1 Verificação forte

STAGING_FILES="$(
  find "$STAGING" -type f -printf '.' | wc -c
)"
STAGING_BYTES="$(
  find "$STAGING" -type f -printf '%s\n' |
    awk '{total += $1} END {print total + 0}'
)"

test "$SOURCE_FILES" -eq "$STAGING_FILES"
test "$SOURCE_BYTES" -eq "$STAGING_BYTES"

rsync -rcn \
  --no-perms --no-owner --no-group \
  --delete --itemize-changes \
  "$SOURCE/" "$STAGING/"
Resultado esperado: os testes não produzem saída e o último rsync também fica vazio. Ele calcula checksums e pode demorar, mas não altera nem apaga nada porque usa --dry-run.

5Publicar no Files do usuário

Normalize os nomes para Unicode NFC ainda no staging. O Nextcloud rejeita acentos decompostos, comuns em arquivos vindos de SMB/macOS:

python3 - "$STAGING" <<'PY'
import os
import sys
import unicodedata

root = os.path.abspath(sys.argv[1])
plan = []
for base, directories, files in os.walk(root):
    for name in directories + files:
        normalized = unicodedata.normalize("NFC", name)
        if normalized != name:
            plan.append((
                os.path.join(base, name),
                os.path.join(base, normalized),
            ))

collisions = [
    (source, destination)
    for source, destination in plan
    if os.path.lexists(destination)
]
if collisions:
    raise SystemExit(
        f"Colisões após normalização: {len(collisions)}"
    )

for source, destination in sorted(
    plan,
    key=lambda pair: pair[0].count(os.sep),
    reverse=True,
):
    os.rename(source, destination)

print(f"Nomes normalizados para NFC: {len(plan)}")
PY
Resultado esperado: o comando informa quantos nomes foram normalizados e não relata colisões. O conteúdo dos arquivos não é modificado.

Normalize ownership e permissões:

chown -R 33:33 "$STAGING"
find "$STAGING" -type d -exec chmod 0750 {} +
find "$STAGING" -type f -exec chmod 0640 {} +

test ! -e "$DESTINATION"
mv -- "$STAGING" "$DESTINATION"
test -d "$DESTINATION"
Resultado esperado: nenhuma saída. Como staging e destino estão no mesmo ext4, o mv apenas renomeia o diretório e não faz uma segunda cópia.

Registre somente a pasta importada no banco do Nextcloud:

docker exec -u www-data nextcloud-app \
  php occ files:scan \
  --path="$NC_USER/files/$IMPORT_NAME"
Resultado esperado: tabela final com Errors = 0 e contagem de arquivos compatível com SOURCE_FILES.
Se o scan falhar, não apague a pasta publicada. Corrija o erro e repita o mesmo occ files:scan --path.

Validação humana

7Desmontar e limpar

Somente depois da validação humana:

umount "$SMB_MOUNT"
findmnt "$SMB_MOUNT" && exit 1 || true

rm -f -- "$CREDENTIALS"
rmdir "$SMB_MOUNT"
rmdir "$STAGING_ROOT" 2>/dev/null || true

test ! -e "$CREDENTIALS"
test ! -e "$SMB_MOUNT"
Resultado esperado: nenhuma saída dos testes finais. Isso remove somente a credencial SMB temporária criada na VM Nextcloud; não altera o arquivo local C:\Users\rcass\.copilot\server-password.txt.
A importação está concluída quando a UI mostra todos os arquivos, o scan terminou sem erros, origem e destino possuem as mesmas contagens e o share antigo está desmontado.

!Falhas comuns

SintomaAção
No route to host ou timeout na porta 445 Corrigir rota/firewall entre 10.0.77.0/24 e 192.168.15.0/24.
mount error(13): Permission denied Revisar usuário, senha, nome do share e permissões no Windows.
mount error(95): Operation not supported Tentar vers=2.1; não habilitar SMB1.
Dry-run por checksum lista diferenças Repetir a cópia real e depois executar novamente a verificação.
Arquivos existem no disco, mas não aparecem na UI Repetir occ files:scan --path com usuário e path corretos.
