Disco dedicado para o Nextcloud no Proxmox

Criação do zero, shares locais vazios, migração técnica do volume interno, mudança dos mounts Docker e desligamento reversível do fileserver.

Etapas: Arquitetura Preparar Proxmox Filesystem Storage vazio Cutover Validar Operar Rollback

0Arquitetura recomendada

HD/Storage físico no Proxmox │ └── disco virtual SCSI exclusivo │ ▼ VM Nextcloud /dev/sdX1 (ext4) /srv/nextcloud-storage ├── app-data/ └── shares/ ├── publico/ ├── usuarios/ ├── laudos/ │ └── mega/ └── administrativo/ │ ▼ bind mounts container nextcloud-app
Nunca anexe o mesmo ext4 simultaneamente à VM Nextcloud e à VM fileserver. Um filesystem comum não é cluster-aware; multiattach pode causar corrupção silenciosa. Enquanto o disco estiver na VM Nextcloud, o Samba de outra VM não poderá usar esse caminho diretamente.
Este guia não transforma o novo disco em share Samba e não copia os arquivos dos shares antigos. Ele cria armazenamento local vazio para o Nextcloud e deixa a VM fileserver preservada para rollback. Se Samba voltar no futuro, será necessário decidir quem será novamente a fonte de verdade.

Os paths novos usados neste procedimento são:

UsoPath no host NextcloudPath no container
Dados internos Nextcloud/srv/nextcloud-storage/app-data/var/www/html/data
Shares locais novos e vazios/srv/nextcloud-storage/shares/mnt/storage/shares

1.1 Levantar uso atual

Na VM Nextcloud:

df -hT
du -sh /mnt/nextcloud-data/* 2>/dev/null
docker volume inspect docker_nc_data \
  --format '{{.Mountpoint}}'
docker system df

Escolha um disco com folga para crescimento. Não use exatamente o tamanho atual.

1.2 Snapshots obrigatórios

Antes de particionar, migrar o volume interno ou recriar containers, faça snapshots da VM fileserver, VM Nextcloud e CT cloudflared. Confirme no Proxmox que terminaram. Marque o novo disco como incluído em backup.

1.3 Backup lógico do banco

Na VM Nextcloud:

install -d -o root -g root -m 0700 /root/backup-nextcloud
DB_BACKUP="/root/backup-nextcloud/all-databases-$(date -u +%Y%m%dT%H%M%SZ).sql"

docker exec docker-db-1 sh -c '
  tmp=/tmp/backup-client.cnf
  trap "rm -f $tmp" EXIT
  umask 077
  printf "[client]\nuser=root\npassword=%s\n" \
    "$MYSQL_ROOT_PASSWORD" >"$tmp"
  mariadb-dump \
    --defaults-extra-file="$tmp" \
    --single-transaction \
    --routines --triggers --events \
    --all-databases
' >"$DB_BACKUP"

chmod 0600 "$DB_BACKUP"
test -s "$DB_BACKUP"

1.4 Consequências de desligar o Samba

  • o Samba deixa de ser a fonte ativa de usuários e grupos;
  • o exportador e o sync Samba → Nextcloud devem ser desabilitados;
  • novos usuários deverão ser administrados diretamente no Nextcloud;
  • ACLs Samba não serão copiadas como autorização; os grupos Nextcloud controlarão os External Storages;
  • não execute lifecycle enquanto o fileserver estiver desligado.
Se também não quiser preservar arquivos pessoais já enviados diretamente ao Nextcloud, exclua-os pela interface do próprio Nextcloud e esvazie a lixeira antes da janela. Não omita seletivamente pastas do volume docker_nc_data: esse volume deve ser migrado integralmente para permanecer consistente com o banco.

2Adicionar o disco virtual no Proxmox

  1. Abra a VM Nextcloud no Proxmox.
  2. Entre em Hardware → Add → Hard Disk.
  3. Use barramento SCSI.
  4. Escolha o storage físico desejado e informe o tamanho.
  5. Marque Backup.
  6. Habilite Discard se o storage suportar.
  7. Use SSD emulation somente se o backend for SSD.
  8. Confirme a adição. Não use compartilhamento/multiattach.
O recomendado é criar um disco virtual no storage do Proxmox, não passar uma partição física diretamente. Isso preserva snapshots, backup, mobilidade e controle pelo hypervisor.

Na VM Nextcloud, identifique o disco novo pelo tamanho:

lsblk -e7 -o NAME,SIZE,TYPE,FSTYPE,LABEL,UUID,MOUNTPOINTS,MODEL
sudo fdisk -l
Nos exemplos seguintes usamos /dev/sdb. Substitua pelo disco realmente novo. Escolher o disco errado destrói dados.

3Criar filesystem e mount permanente

Instale as ferramentas e faça uma inspeção sem modificar:

apt-get update
apt-get install -y parted e2fsprogs rsync jq

DISCO="/dev/sdb"
wipefs -n "$DISCO"
lsblk "$DISCO"
O bloco abaixo é destrutivo para $DISCO. Execute somente depois de confirmar duas vezes o device. 
read -r -p "Digite APAGAR-$DISCO para continuar: " CONFIRMA
[[ "$CONFIRMA" == "APAGAR-$DISCO" ]] || exit 1

parted -s "$DISCO" mklabel gpt
parted -s "$DISCO" mkpart primary ext4 1MiB 100%
udevadm settle

PARTICAO="${DISCO}1"
mkfs.ext4 -L NC_STORAGE "$PARTICAO"

Descubra o UUID e monte em um path totalmente novo:

UUID_NC="$(blkid -s UUID -o value "$PARTICAO")"
test -n "$UUID_NC"

install -d -o root -g root -m 0750 /srv/nextcloud-storage
! grep -Fq ' /srv/nextcloud-storage ' /etc/fstab
printf 'UUID=%s /srv/nextcloud-storage ext4 defaults,noatime 0 2\n' \
  "$UUID_NC" >>/etc/fstab

systemctl daemon-reload
mount /srv/nextcloud-storage
findmnt --verify
findmnt /srv/nextcloud-storage
Não use nofail. Se o disco não montar, o boot/Docker deve falhar fechado; caso contrário, dados podem ser gravados por engano no disco raiz sob o diretório vazio.

Crie a estrutura nova:

install -d -o 33 -g 33 -m 0770 \
  /srv/nextcloud-storage/app-data
install -d -o 33 -g 33 -m 0750 \
  /srv/nextcloud-storage/shares

for dir in publico usuarios laudos administrativo; do
  install -d -o 33 -g 33 -m 0770 \
    "/srv/nextcloud-storage/shares/$dir"
done
install -d -o 33 -g 33 -m 0770 \
  /srv/nextcloud-storage/shares/laudos/mega

docker exec nextcloud-app id www-data
stat -c '%a %u:%g %n' /srv/nextcloud-storage \
  /srv/nextcloud-storage/app-data \
  /srv/nextcloud-storage/shares/*

3.1 Fazer o Docker depender do mount

install -d -o root -g root -m 0755 \
  /etc/systemd/system/docker.service.d

cat >/etc/systemd/system/docker.service.d/nextcloud-storage.conf <<'EOF'
[Unit]
RequiresMountsFor=/srv/nextcloud-storage
EOF

chmod 0644 \
  /etc/systemd/system/docker.service.d/nextcloud-storage.conf
systemctl daemon-reload

4Preparar os shares vazios

Nenhum arquivo dos shares Samba será copiado. Os dados antigos permanecem intactos no fileserver desligado para eventual consulta ou rollback manual.

Confirme que os destinos estão vazios antes do cutover:

find /srv/nextcloud-storage/shares -mindepth 1 \
  -type f -print -quit

test -z "$(
  find /srv/nextcloud-storage/shares -mindepth 1 \
    -type f -print -quit
)"

stat -c '%a %u:%g %n' \
  /srv/nextcloud-storage/shares \
  /srv/nextcloud-storage/shares/* \
  /srv/nextcloud-storage/shares/laudos/mega

O primeiro comando não deve listar arquivo algum. A árvore laudos/mega é intencional: Laudos-Mega é uma visão do subdiretório físico de Laudos, não uma segunda cópia.

5Cutover e desligamento do Samba

Esta etapa muda a origem dos dados e recria o container Nextcloud. Comece somente dentro da janela, com snapshots concluídos.

5.1 Congelar gravações

Na VM Nextcloud:

      systemctl stop \
        nextcloud-cron.timer \
        nextcloud-files-scan.timer \
        sync-nextcloud-state.timer

      for service in \
        nextcloud-cron.service \
  nextcloud-files-scan.service \
  sync-nextcloud-state.service
do
  systemctl is-active --quiet "$service" && {
    echo "Aguarde o service terminar: $service" >&2
    exit 1
  }
done

docker exec -u www-data nextcloud-app \
  php occ maintenance:mode --on

No fileserver, pare apenas a geração de novos snapshots. Não é necessário congelar ou copiar os shares antigos:

smbstatus
systemctl stop export-nextcloud-state.timer

5.2 Migrar somente o data directory técnico

Esta cópia não importa os shares Samba. Ela preserva o estado interno da instalação Nextcloud atual, como .ocdata, appdata_* e a consistência com o banco. Trocar por um diretório vazio sem reinstalar o Nextcloud não é suportado. 
cd /home/rafael/git/scripts_servidor/nextcloud/docker
docker compose stop app

NC_DATA_SOURCE="$(
  docker volume inspect docker_nc_data \
    --format '{{.Mountpoint}}'
)"
test -d "$NC_DATA_SOURCE"

rsync -aHAX --numeric-ids --info=progress2 \
  "$NC_DATA_SOURCE/" \
  /srv/nextcloud-storage/app-data/

rsync -aHAXn --numeric-ids --itemize-changes \
  "$NC_DATA_SOURCE/" \
  /srv/nextcloud-storage/app-data/

O dry-run final também deve ficar vazio.

5.3 Alterar o Compose

Faça backup antes de editar:

cp -a docker-compose.yml \
  "/root/docker-compose.before-local-disk.$(date -u +%Y%m%dT%H%M%SZ).yml"

No serviço app, remova:

- nc_data:/var/www/html/data
- /mnt/nextcloud-data/publico:/mnt/samba/publico
- /mnt/nextcloud-data/usuarios:/mnt/samba/usuarios
- /mnt/nextcloud-data/laudos:/mnt/samba/laudos
- /mnt/nextcloud-data/laudos-mega:/mnt/samba/laudos-mega
- /mnt/nextcloud-data/administrativo:/mnt/samba/administrativo

E adicione:

- /srv/nextcloud-storage/app-data:/var/www/html/data
- /srv/nextcloud-storage/shares:/mnt/storage/shares

Valide antes de subir:

docker compose config --quiet
docker compose config | sed -n '/volumes:/,/networks:/p'
findmnt /srv/nextcloud-storage

5.4 Subir e ajustar External Storages

docker compose up -d

for attempt in $(seq 1 60); do
  docker exec -u www-data nextcloud-app \
    php occ status --output=json && break
  sleep 5
done

Mantenha maintenance mode ligado. Ajuste os storages existentes por nome, sem assumir IDs numéricos:

occ() {
  docker exec -u www-data nextcloud-app php occ "$@"
}

set_storage_path() {
  local mount_point="$1"
  local new_path="$2"
  local id
  id="$(
    occ files_external:list --output=json |
      jq -r --arg mount "$mount_point" \
        '.[] | select(.mount_point == $mount) | .mount_id'
  )"
  [[ "$id" =~ ^[0-9]+$ ]] || {
    echo "Storage ausente ou duplicado: $mount_point" >&2
    return 1
  }
  occ files_external:config "$id" datadir "$new_path"
}

set_storage_path "/Publico" \
  "/mnt/storage/shares/publico"
set_storage_path "/Minha pasta" \
  '/mnt/storage/shares/usuarios/$user'
set_storage_path "/Usuarios - Administração" \
  "/mnt/storage/shares/usuarios"
set_storage_path "/Laudos" \
  "/mnt/storage/shares/laudos"
set_storage_path "/Laudos-Mega" \
  "/mnt/storage/shares/laudos/mega"
set_storage_path "/Administrativo" \
  "/mnt/storage/shares/administrativo"

occ files_external:list

Confira também os grupos:

Não reative sync-nextcloud-state.timer enquanto Samba e o exportador estiverem desligados.

5.5 Remover a dependência CIFS

Somente após validar o novo storage:

cp -a \
  /etc/systemd/system/docker.service.d/nextcloud-cifs.conf \
  /root/nextcloud-cifs.conf.backup

rm -f \
  /etc/systemd/system/docker.service.d/nextcloud-cifs.conf
systemctl daemon-reload

Edite `/etc/fstab` e comente somente as cinco linhas CIFS antigas. Depois desmonte sem usar opções forçadas:

umount /mnt/nextcloud-data/publico
umount /mnt/nextcloud-data/usuarios
umount /mnt/nextcloud-data/laudos
umount /mnt/nextcloud-data/laudos-mega
umount /mnt/nextcloud-data/administrativo

findmnt --verify
mount -a

5.6 Desligar o Samba, sem apagar nada

No fileserver:

systemctl disable --now export-nextcloud-state.timer
systemctl disable --now smbd
systemctl disable --now nmbd 2>/dev/null || true

systemctl is-active smbd
systemctl is-enabled smbd
Não exclua a VM fileserver, usuários, TDBs, ACLs ou dados originais. Desligue a VM e mantenha os snapshots durante o período de aceitação.

7Operar sem o Samba

Novos usuários

Crie a conta e os grupos diretamente no Nextcloud. Como o storage Minha pasta usa $user, crie também o diretório correspondente na VM Nextcloud:

USUARIO="novo_usuario"
[[ "$USUARIO" =~ ^[a-z_][a-z0-9_-]*$ ]] || exit 1

install -d -o 33 -g 33 -m 0770 \
  "/srv/nextcloud-storage/shares/usuarios/$USUARIO"

Não recrie o usuário no Samba enquanto esta arquitetura estiver ativa. O timer sync-nextcloud-state.timer deve continuar desabilitado.

RRollback

Se qualquer validação falhar antes de liberar usuários:

  1. ative maintenance mode;
  2. pare o container app;
  3. restaure o `docker-compose.yml` anterior;
  4. restaure o drop-in CIFS;
  5. remova o drop-in do disco novo;
  6. descomente as cinco linhas CIFS no `fstab`, comente o mount do disco novo e monte os CIFS;
  7. ligue a VM fileserver e o `smbd`;
  8. suba o Compose anterior;
  9. restaure os seis paths dos External Storages;
  10. restaure os timers somente após validar.

No fileserver:

systemctl enable --now smbd

Não copie dados de volta automaticamente após o novo storage receber gravações. Isso exige reconciliação bidirecional e decisão explícita sobre qual lado é a fonte correta.

Depois da aceitação

  • mantenha a VM fileserver desligada por um período acordado;
  • faça backup do novo disco e teste restauração;
  • documente que usuários passam a ser geridos no Nextcloud;
  • revise retenção dos snapshots antes de removê-los;
  • não apague os dados Samba sem aprovação separada.
Migração Samba → armazenamento local Nextcloud. Guia operacional; revise devices, UUIDs e paths antes de executar comandos destrutivos.
